**Editor-discoverable artifact pair** ([#103](https://github.com/arthur-debert/clapfig/issues/103)) — `Builder::artifacts(&options)` (and its `TypedBuilder` twin) renders the config template and its JSON Schema document from the one `Shape` the builder holds, and can prefix the template with the editor schema directive a TOML language server reads to validate a config file as the user types it. Additive: `ConfigAction::Gen`'s fields are unchanged and there is no new CLI behavior.

- **The pair.** `ConfigArtifacts { template, schema }`, returned as strings — clapfig writes nothing. The template body is what `config gen` renders in the preferred format; the schema text is what `config schema` emits. Both entry points have the method (runtime `Shape` and `#[derive(Schema)]`), and both generate from the same schema.
- **The directive.** With a reference set, the template's first line is exactly `#:schema <reference>` and a blank line separates it from the body. It is an ordinary TOML comment, so a file carrying it loads and strict-validates as before.
- **The reference is the caller's.** `SchemaReference::new` validates one line — rejecting empty, whitespace-only, line-break-carrying, control-character-carrying, and surrounding-whitespace values as `ClapfigError::InvalidSchemaReference` — and is otherwise opaque: no path resolution, no reachability check, no reference inferred from an output path. The caller owns the path or URL, the filesystem layout, writing both files, and publication/versioning.
- **Format capability** (ADR-0002 matrix row `Operation::SchemaDirective`). TOML declares it; YAML and JSON do not, so asking for a reference under either refuses with the typed `UnsupportedByFormat` error instead of dropping the binding. No JSON `$schema` member and no YAML language-server comment.
- **`normalize_keys` reaches the JSON Schema.** With `.normalize_keys(true)`, `config schema` and the pair's schema name every multiword key twice — the kebab-case spelling the template writes (`pool-size`) and the declared snake_case one (`pool_size`) — because that builder loads either. Object schemas are closed, so a document naming just one spelling would make an external validator reject a file clapfig reads: the template beside it, or a hand-written snake_case config. A key written under both spellings at once is rejected, the way the load path refuses that collision. Applies to nested and map-entry fields and to tagged tag keys and variant fields; discriminator values, doc comments, and defaults are unchanged.
- **The one pairing that refuses.** A schema *declaring* a key that already holds a `-` (`rename_all = "kebab-case"`, `SCREAMING-KEBAB-CASE`, an explicit rename) is unreachable under `.normalize_keys(true)`: normalization rewrites the `-` to `_` before validation, so no written spelling matches the declared name and loading already fails every document. `config gen`, `config schema`, and `artifacts()` now refuse that combination with the new `ClapfigError::UnreachableNormalizedKey`, naming the key, its section, and the spelling it arrives under, instead of emitting a template or schema under names the same builder's loader rejects. Checked at every depth — nested fields, array and map entry fields, tagged tag keys and variant fields. Either supported pairing is untouched: a kebab-declared schema without normalization, and normalization over a snake_case one.
- **Opt-out is the default.** Without a reference, template and schema are byte-for-byte the standalone actions' output.
- **Consumer proof.** `bin/tombi-proof.sh` generates an edward-shaped pair through the `schema_directive` example and runs a pinned tombi against it: the template validates, a filled-in instance validates under either spelling of its multiword key, and both spellings at once — as well as an unknown key — are rejected.
